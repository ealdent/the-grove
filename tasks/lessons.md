- Always properly dispose Three.js meshes, materials, and geometries when removing objects from the scene to prevent memory leaks in long-running apps.
- When maintaining a finite number of positions for objects (like task slots), implement an array or stack of available indices and ensure indices are reclaimed when objects are removed.
- For 2D canvas games, cache complex static vector layers (roads, pebbles, grass, decorations) onto an offscreen canvas. Recalculate buffs (like booster towers) statically when towers are placed, upgraded, or sold instead of doing O(N^2) calculations on every physics tick. Render numerous small particles using fillRect rather than beginPath/arc/fill path calls.
- When implementing delta-time (frame-rate independence) in a game loop, ensure that all base speeds, progress increments, particle velocities, and frame-decay timers are scaled appropriately (usually by multiplying by 60 for target 60fps base values) so they do not run 60x slower in real-time. Also, remove heavy CSS features like backdrop-filter from UI panels surrounding the canvas, as they cause massive GPU composite lag on every repaint.
- When drawing real-device training diagrams, verify the physical left/right orientation from the user's viewing angle before placing hotspots. Prefer high-contrast label pills and generous hotspot spacing over decorative schematic labels when the diagram is meant for matching a device in hand.
- Decorative overlays and pseudo-elements in front of interactive UI must use `pointer-events: none` or live behind content with explicit stacking, especially when only one grid column fails hover/click behavior.
- ALWAYS clamp gl_PointSize in every THREE.Points system (use a ShaderMaterial with `clamp(...)`, never raw `sizeAttenuation`). A particle that drifts through the camera gets a size of size×scale/distance → thousands of pixels, and oversized points rasterize as giant garbage-black quads on some GPU backends (Chrome/ANGLE on Metal).
- For "photorealism" in procedural Three.js scenes, the highest-leverage fixes in order: (1) IBL must match the setting — generate the environment map from the scene's own Sky instead of RoomEnvironment, whose studio panels reflect as fake white blobs; (2) no emissive on organic materials — use sheen; (3) per-vertex color gradients on petals/leaves (flat single colors read as toys); (4) fBm-based texture variation (damp patches, weathering, grime) instead of uniform speckle noise.
- After merging a PR through an API/MCP tool, verify the result: diff the merged main against the branch tip (`git diff origin/main origin/<branch> -- <files>`). A merge executed against a stale head silently drops the newest commits.
- When restyling an existing game's high-salience identity, preserve its iconic anchors unless the user explicitly asks to replace them. For Redline Ascent, the oversized hot-red pixel marquee, warm CRT halo, and dark grime matter more than applying a cleaner design system uniformly; compare the old and new hero state before handoff.
- Volumetric light (godray cones, light shafts, fog volumes) must ABSORB as well as emit. `AdditiveBlending` can only brighten, so the background keeps its full contrast and shows straight through the beam as a ghostly negative image. Real media is `bg * T + L`; setting `L = colour * (1 - T)` makes that ordinary alpha-over, so use `NormalBlending` with alpha as *density* and a colour whose components exceed 1 so the dense core tone-maps to a glow instead of flat paint. Bonus: when every fragment emits the same colour, alpha-over is order-independent (`c·(a₁+a₂−a₁a₂)` either way), so a single InstancedMesh of overlapping cones needs no depth sorting.
- Additive volumetrics also need a *near-camera* fade (`smoothstep(1.0, 4.5, length(viewPos))`). The shaft you are standing inside fills the screen and paints everything behind it; fading it out within a few metres is both what real godrays look like and the single biggest fix for "it's washing out the whole scene". Prove which layer causes a wash by pinning its intensity uniform to 0 and re-shooting — don't guess between the light and the haze.
- Soft edges on a volumetric cone come from `alpha *= pow(abs(dot(normal, viewDir)), k)` — peak down the axis where a sightline crosses the most air, zero at the silhouette. It removes the hard geometric outline and approximates real path length. Keep the fade ramp at the emitter end SHORT, or the glow bleeds over the fixture and the lampshade loses its edge.
- A backtick inside a GLSL comment terminates the JS template literal holding the shader — the module then fails to parse with a bewildering error like `Unexpected identifier 'bg'`, the page silently renders nothing, and the browser console stays EMPTY. Never use backticks in shader comments, and run a parse check (`new vm.SourceTextModule(fs.readFileSync(...))`) after every shader edit rather than only at the end.
- Symptom-to-cause for "my edit didn't take": `window.<handle>` undefined + `document.querySelectorAll('canvas').length === 0` + no console errors means the module never executed, i.e. a syntax error — not a caching problem. Confirm by fetching the served file and checking it contains the edit, then parse it.
- three.js `scene.environmentIntensity` did not exist until r163. On r160 it is a silently ignored property, so an env-map dimming line does nothing and the IBL stays at full daytime brightness after dark. Dim the PMREM *source* scene instead. Removing that accidental night fill will make the scene noticeably darker — expect to re-tune, and note that raising a HemisphereLight barely helps when nearly every surface is lit by local lamps; night `toneMappingExposure` is the dial that actually lifts the shadows, and ACES protects the highlights.
- Metal light fixtures must not carry `emissive`. It lights the *outside* of the shade too and turns each fixture into a floating ember; let the bulb be the only emitter and let the geometry aim the light.
- With `MeshPhysicalMaterial` transmission, anything meant to be seen THROUGH the glass must be in the **opaque** draw list, because three builds its transmission buffer from that list alone. A transparent star field or backdrop simply does not exist as far as the glass is concerned. Use `transparent: false` plus `alphaTest` (and `discard` in custom shaders) rather than `transparent: true` — on a dark sky "replace" and "add" look identical anyway.
- Painted-backdrop cylinders quietly eat the sky. A backdrop that paints its own sky gradient above the canopy is an opaque *dome*, not a tree line: it blocks every sightline below its top edge (44 m at r=64 → 33° elevation) and, since such materials are usually dimmed by nightness, that whole band goes pitch black after dark. Give the canopy an alpha silhouette and let the real sky show above it.
- Don't order sky elements by radius in three. The opaque list is sorted by each object's *origin*, and a Sky box and a camera-tracking star dome both sit on the viewer, so their sort keys are both ~0 and their relative order is arbitrary. Set `renderOrder` explicitly (sky -3, stars -2, moon -1) with `depthWrite: false`, and let the world paint over them — that is also what gives correct occlusion.
- For a night sky, `SunCalc`'s moon ephemeris is ~25 lines on top of the sun code already present (`moonCoords` + `getMoonIllumination`) and gives real altitude, azimuth, phase fraction and bright-limb angle. Verify it against published new/full moon dates before trusting it. The bright-limb *angle* matters: without it a gibbous moon's terminator sits vertically and looks wrong.
- A true-scale moon (0.52°) renders ~8 px at 1080p/70° FOV and disappears among the stars — exaggerate to ~1.5-2°. And when a small bright object "isn't rendering", check it isn't simply sitting behind a centred DOM overlay before debugging the shader: swap in a flat `MeshBasicMaterial` at 4x scale to separate transform/visibility problems from shader problems.
- `makeFbmField(size, octaves, baseFreq)` requires an **integer** `baseFreq`. It indexes its lattice with `gy % freq`, so a fractional frequency gives fractional indices, every lookup is `undefined`, and the whole field comes back NaN. NaN then lands in a `Uint8ClampedArray` as 0 — so the failure is silent and spectacular: a black albedo *and* a roughness map of zero, i.e. mirror-finish surfaces reflecting the sky as flat blue sheets, with nothing in the console. Symptom-to-cause: a material that suddenly reflects the environment perfectly and has lost its texture means its roughness map is all zeros, which almost always means a NaN in the generator.
- Painted texture features have to be sized in **world units, not texels**. A 4 px dot in a 512 px tile that repeats every 16.7 m is a 13 cm stone; 260 of those, lighter than the soil around them, read from eye height as pale discs scattered over the floor like dropped coins. Grit reads as grit only when it is many, small, and low-contrast against its base.
- Volumetric alpha and volumetric radiance are separate dials, and re-tuning the room's ambient invalidates both. Cones tuned to "peak alpha 1.0, colour ×1.7" against a generous ambient fill became opaque milk-glass lampshades once night ambient dropped to near-black. A beam wants peak alpha around 0.5–0.6 (remember `DoubleSide` compounds it as `1-(1-a)²`) and just enough radiance to tone-map warm.
- A fog *sheet* needs the inverse of a light cone's facing term: `pow(1 - |dot(n, viewDir)|, k)`. A horizontal plane seen face-on is millimetres of air and must contribute nothing; seen along its length it is metres. Without it the layer nearest the camera lands on the floor as a flat white smear. And fade *every* edge of the plane, sides as well as ends, or its own boundary shows as a straight-edged rectangle in the near corners.
- Before deciding a small bright object "isn't rendering", check what opaque geometry encircles the playfield. A painted backdrop cylinder at r=64 hides anything placed at 75 m absolutely — and a centred DOM crosshair hides anything you aim exactly at. Prove it renders by scaling it up 6x first; a faint wash at 6x means "dim and occluded", not "broken".
- In three.js, `shadow.autoUpdate = false` + `shadow.needsUpdate = true` on demand is the single biggest win available in a static scene. This greenhouse rendered 25 shadow passes per frame (a 2048² directional plus four point-light *cube* maps) for pictures identical to the previous frame; nothing that cast a shadow ever moved. Invalidate on: the sun/moon tick, a shadow-casting light being repositioned, and geometry being added or removed. Do NOT invalidate from a per-frame visual update (plant growth) — sub-millimetre staleness for 30 s is invisible and defeats the whole optimization.
- To swap which lights cast shadows as the camera moves, **reassign a fixed pool to positions** rather than toggling `castShadow`. Toggling changes `numPointLightShadows`, which recompiles every material in the scene. Identical fixtures make the swap unobservable, and the light and shadow counts then never change after startup.
- Headless Chrome under `--virtual-time-budget` hands `requestAnimationFrame` a delta of ~0, so anything integrated over real time (a filament warm-up, a flicker, a sway) freezes after one frame and cannot be observed at all. Expose a deterministic stepper on the debug object (`advanceLamps(dt, steps)`) that calls the updater with a synthetic delta — that is the only way to get a real measurement, and it doubles as the artifact you paste into the commit message.
